# Правила разработки

Документы: `../PRD-interior-planner.md`, `../SPEC.md`, `../Tasks.md`. Работа строго по одному этапу Tasks.md (D-19).

## Принципы кода (D-21)

- **DRY.** Одно знание — одно место. Геометрия (чистые прямоугольники, площади, единицы) считается только функциями `src/domain` и `src/geometry`; 2D, 3D и интерфейс их вызывают, а не повторяют формулы. Константы (допуск, пределы §3.2) — в одном модуле.
- **SRP.** Модуль отвечает за одно: модель данных, геометрия, проверки, команды, состояние, представление. Геометрические функции не зависят от React, SVG и Three.js.
- **OCP.** Новые проверки добавляются как новые валидаторы в общий список (`src/domain/validation.ts`), без правки контракта применения изменений.
- **LSP / ISP.** Небольшие типы под задачу: команда — чистая функция `Apartment → Apartment`; валидатор — `Apartment → Issue[]`.
- **DIP.** Хранилище и интерфейс зависят от абстракций (команда, валидатор), а не от конкретных изменений.
- Без лишних абстракций: SOLID не повод для слоёв «на будущее» (см. скилл karpathy-guidelines — простота прежде всего).

## Команды

`npm run lint`, `npm run typecheck`, `npm run build`; всё вместе — `npm run check`. Тесты: `npm test`, `npm run e2e -- --workers=1`.

## Проверка этапов (D-23)

- После каждого этапа — только `npm run check` (линтер oxlint, проверка типов, сборка). Unit- и e2e-тесты после этапов не запускаются и новые тесты по этапам не пишутся.
- Один общий контрольный тест всего приложения — после окончания всего проекта.
- Визуальную проверку (кадр через `scripts/capture-*.mjs`) делать, когда этап меняет внешний вид.

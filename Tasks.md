## Как агенту отмечать выполнение

- `[ ]` — не завершено; `[ ]` — выполнено и проверено. Нумерация стабильная: шаг 1, подпункты 1.1, 1.2 и далее.
- Перед началом подпункта записать его номер в «Текущая работа». Не ставить галочку до завершения проверки.
- После завершения заменить `[ ]` на `[ ]` и добавить запись в журнал: номер, дата, результат, изменённые файлы и проверка. Путь к файлу, отчёт или команда с результатом должны позволять перепроверить работу.
- Родительский шаг отмечать только после завершения всех его обязательных подпунктов. Частично реализованная задача остаётся `[ ]` с пояснением.
- Блокировку обозначать текстом `Блокировано: D-XX, требуется …`; оставлять `[ ]`. Не отмечать ожидание ответа, отсутствие ошибки или написанный план как выполненную функцию.
- Отложенный по решению пользователя пункт остаётся `[ ]` с записью `Отложено: дата, решение`. Он исключается из конкретного релиза только после фиксации изменения объёма. Не использовать `[ ]` для пропущенной работы.
- Работать строго по одному этапу: следующий этап начинается только после завершения текущего и подтверждения пользователя. Решение этапа 1 считается закрытым при наличии ответа или явной записи «отложено» с указанием того, что без него не будет сделано. Соблюдать зависимости ниже.
- Если проверка обнаружила регрессию, снова открыть соответствующий чекбокс и записать причину в журнал. Не удалять историю.
- Все изменения требований отражать в SPEC и, при изменении продуктового объёма, в PRD. Новые решения пользователя записывать в SPEC §3. Новые задачи добавлять без перенумерации уже использованных идентификаторов.
- Установка скилла, написание кода и прохождение проверки — разные результаты. Отмечать только тот подпункт, который действительно выполнен.
- С этапа 13 (D-23): после этапа запускается только `npm run check` (линтер, типы, сборка); unit- и e2e-тесты — один общий контрольный прогон в конце проекта. В журнале указывать, что поведенческая проверка подпункта отложена до контрольного теста.
